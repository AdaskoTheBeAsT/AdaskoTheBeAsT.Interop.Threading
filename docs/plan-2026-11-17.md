## Executive summary

Auditing production native/COM wrappers and STA test suites surfaced **five recurring threading, STA apartment, locale, and timeout patterns** that callers previously re-implemented by hand because they sit outside `Interop.COM`, `Interop.Unmanaged`, and `Interop.Execution`:

1. **Synchronous STA execution & `void` (`Action`) overloads (`THR-06`):**
   - [`MutexHelper.RunInMutex`](../src/AdaskoTheBeAsT.Interop.Threading/MutexHelper.cs) requires a synchronous delegate so OS mutex acquisition and `ReleaseMutex()` stay on the same thread. Because [`SingleThreadedApartmentTask`](../src/AdaskoTheBeAsT.Interop.Threading/SingleThreadedApartmentTask.cs) previously exposed only asynchronous `Task<T>` methods (`RunAsync<T>` / `RunWithTimeoutAsync<T>`) and lacked `Action` overloads, callers (cross-process mutex-serialized STA calculators and STA integration test suites) hand-rolled `RunOnStaThread` around `new Thread` + `SetApartmentState(STA)` + `Join()`.
   - Those ad-hoc helpers skip `OleInitialize`, skip native `CoGetApartmentType` verification and Nano Server `CoInitializeEx(COINIT_APARTMENTTHREADED)` recovery, skip the bounded final message pump before teardown, and handle exceptions inconsistently. In addition, `SingleThreadedApartmentTask.RunAsync` itself did not yet run `THR-01` native STA apartment verification after `OleInitialize`.
2. **Portable thread-ownership guard & standalone native STA apartment scope (`THR-07`):**
   - Over a dozen stateful COM, native P/Invoke, and pooled session classes copy-pasted `_owningThreadId = Environment.CurrentManagedThreadId` and `EnsureOwningThread()` / `CheckThread()`.
   - Multiple STA COM runtimes also duplicated `CoGetApartmentType` checks plus balanced `CoInitializeEx(0, COINIT_APARTMENTTHREADED)` / `CoUninitialize()` leases when hosted on external STA threads (such as `ExecutionWorkerPool<TSession>` with `UseStaThread = true` or `[StaFact]` test threads). CoreCLR initializes `ApartmentState.STA` worker threads via internal `RoInitialize(0x40000000)`, which skips registering `"OleMainThreadWndClass"` in `combase.dll` until an explicit `CoInitializeEx(COINIT_APARTMENTTHREADED)` or `OleInitialize` call runs on that thread; without it, contended `Lock` / `WaitHandle` waits entering `CoWaitForMultipleHandles -> GetOrCreateSTAWindow` can fail.
3. **Managed thread culture & Win32 kernel thread locale (`SetThreadLocale`) pinning and hygiene (`THR-08`):**
   - Legacy VB6 (`CStr`/`CDbl`, `OLEAUT32!VarBstrFromR8`/`VarR8FromStr`), Delphi (`SysUtils` format settings seeded from `GetThreadLocale`), and Jet/DAO engines parse and format numbers using **both** managed `CultureInfo.CurrentCulture` and the Win32 kernel thread LCID (`kernel32!SetThreadLocale`, e.g., `0x0409` `en-US` or `0x0809` `en-GB`).
   - Production VB6/Delphi STA session wrappers manually reset `CultureInfo.CurrentCulture`, `CultureInfo.CurrentUICulture`, and `SetThreadLocale(0x0809)` on startup and before every calculation so host locales (`pl-PL`, `fr-FR`, `de-DE`, `tr-TR`) or mid-call native locale mutations cannot corrupt decimal separators across work items on a shared STA thread.
4. **Single-consumption `ValueTask` & cooperative linked-deadline timeout helpers (`THR-09`):**
   - Downstream dispatcher timeout extensions link caller `CancellationToken` with a deadline `CancelAfter(timeout)`, await a pooled `ValueTask<TResult>` once, attach unobserved-fault suppression when the caller stops waiting, and distinguish caller cancellation (`OperationCanceledException`) from deadline expiry (`TimeoutException`). Generic `ValueTask` (on modern `.NET`) and `Func<CancellationToken, Task>` linked-deadline overloads naturally extend [`TaskExtension.TimeoutAfterAsync`](../src/AdaskoTheBeAsT.Interop.Threading/TaskExtension.cs).
5. **Custom `MaxStackSize` for dedicated STA threads (`THR-10`):**
   - 32-bit Compaq Visual Fortran, Borland Delphi, PowerBASIC, and VB6 binaries allocate large native stack frames while running inside constrained `win-x86` IIS/container virtual address spaces where explicit thread stack sizing (`new Thread(start, maxStackSize)`) prevents `StackOverflowException` or excessive address-space reservation.

## Detailed technical plan

### THR-07 (P0): Portable `ThreadAffinity` guard & standalone Windows `StaApartment` scope

*(Sequenced before `THR-06` and `THR-08` so both reuse the shared apartment and thread-ownership primitives.)*

#### Evidence
- Over a dozen stateful session classes across consuming libraries repeat `_owningThreadId = Environment.CurrentManagedThreadId` and `EnsureOwningThread()` / `CheckThread()`.
- Multiple STA COM runtimes hosted on external STA worker pools manually combine `CoGetApartmentType` checks with `CoInitializeEx(0, COINIT_APARTMENTTHREADED)` / `CoUninitialize()` so `ExecutionWorkerPool` (`UseStaThread = true`) workers register `"OleMainThreadWndClass"` before contended waits and balance COM teardown on `Dispose()`.
- `SingleThreadedApartmentTaskScheduler` already contains internal `EnsureNativeStaApartment` and `IsNativeStaApartment` logic that can be unified in one internal core shared by `SingleThreadedApartmentTaskScheduler`, `SingleThreadedApartmentTask`, and public `StaApartment`.

#### Design
1. **Portable `ThreadAffinity` (`public readonly struct ThreadAffinity : IEquatable<ThreadAffinity>`, available on all TFMs and OSes without `[SupportedOSPlatform("windows")]`):**
   ```csharp
   public readonly struct ThreadAffinity : IEquatable<ThreadAffinity>
   {
       public int OwningThreadId { get; }
       public bool IsInitialized => OwningThreadId != 0;
       public bool IsCurrentThread => OwningThreadId != 0 && OwningThreadId == Environment.CurrentManagedThreadId;

       public static ThreadAffinity Capture() => new(Environment.CurrentManagedThreadId);
       public void ThrowIfWrongThread(string? ownerName = null);
   }
   ```
   - Zero heap allocation (single 4-byte `int` inline in owning session objects).
   - Safe on `default(ThreadAffinity)`: because `Environment.CurrentManagedThreadId` is strictly positive (`>= 1`), `OwningThreadId == 0` never matches the current thread and `ThrowIfWrongThread` throws `InvalidOperationException` indicating an uninitialized affinity guard rather than silently succeeding.
2. **Windows `StaApartment` and `StaApartmentScope` (`[SupportedOSPlatform("windows")]` on `NET8_0_OR_GREATER`):**
   ```csharp
   public static class StaApartment
   {
       public static bool IsCurrentThreadSta(bool verifyNativeApartment = true);
       public static void VerifyCurrentThreadSta(bool verifyNativeApartment = true);
       public static StaApartmentScope EnterScope(bool initializeOle = false);
   }

   public sealed class StaApartmentScope : IDisposable
   {
       public ThreadAffinity Affinity { get; }
       public void Dispose();
   }
   ```
   - `IsCurrentThreadSta(verifyNativeApartment: true)` checks `Thread.CurrentThread.GetApartmentState() == ApartmentState.STA` and queries `combase!CoGetApartmentType`, returning `true` only for `APTTYPE_STA`, `APTTYPE_MAINSTA`, or STA-hosted `APTTYPE_NA` (`APTTYPEQUALIFIER_NA_ON_STA` / `APTTYPEQUALIFIER_NA_ON_MAINSTA`).
   - `EnterScope(bool initializeOle = false)`:
     1. Rejects managed `ApartmentState.MTA` (or native `APTTYPE_MTA` / `RPC_E_CHANGED_MODE`) immediately with `InvalidOperationException` (preserving inner `COMException` when `RPC_E_CHANGED_MODE` is returned).
     2. Calls `CoInitializeEx(IntPtr.Zero, COINIT_APARTMENTTHREADED)` and records `comInitialized = hr >= 0` (`S_OK` and `S_FALSE` both increment `combase`'s apartment reference count and register `"OleMainThreadWndClass"` on CoreCLR `RoInitialize` STA threads).
     3. When `initializeOle` is `true`, calls `OleInitialize(IntPtr.Zero)` (rolling back `CoUninitialize()` if `OleInitialize` fails) and records `oleInitialized = true`.
     4. Verifies native STA apartment membership via the shared `StaPlatform` helper.
     5. Returns an idempotent `StaApartmentScope` bound to `ThreadAffinity.Capture()`. Calling `Dispose()` from a non-owning thread throws `InvalidOperationException` without corrupting the calling thread's COM reference count; calling `Dispose()` multiple times on the owning thread uninitializes at most once (`OleUninitialize()` then `CoUninitialize()`).

#### Acceptance
- Portable unit tests cover `ThreadAffinity.Capture()`, cross-thread `ThrowIfWrongThread(ownerName)`, `default(ThreadAffinity)` rejection, and `IEquatable<ThreadAffinity>`.
- Windows unit tests (simulated `StaPlatform` + live STA/MTA threads across x64 and x86) cover `IsCurrentThreadSta`, `VerifyCurrentThreadSta`, `EnterScope(initializeOle: false | true)`, MTA rejection, partial-initialization rollback when `OleInitialize` fails, idempotent `Dispose()`, and wrong-thread `Dispose()` rejection.

### THR-06 (P0): Synchronous `SingleThreadedApartmentTask.Run`, native STA verification parity & `Action` overloads

#### Evidence
- Cross-process serialized STA COM calculators compose `MutexHelper.RunInMutex(..., () => RunOnStaThread(() => ...))` because `MutexHelper` must hold and release the OS mutex synchronously on the acquiring thread.
- Multiple STA COM test suites define private `RunOnStaThread` helpers to run synchronous xUnit assertions on STA threads.
- `SingleThreadedApartmentTask.Execute<T>` previously called `platform.Initialize()` (`OleInitialize`) without calling `EnsureNativeStaApartment`, leaving one-off STA tasks without Nano Server `CO_E_NOTINITIALIZED` recovery or MTA detection if `OleInitialize` is shimmed.
- Neither `SingleThreadedApartmentTask` nor `MutexHelper` offered `Action` (`void`) overloads, forcing dummy return values (`return true;` / `return 0;`).

#### Design
1. **Bring `SingleThreadedApartmentTask` to native STA verification parity (`THR-01`):**
   - Share the `StaPlatform` native STA verification + `CoInitializeEx(COINIT_APARTMENTTHREADED)` recovery + balanced `CoUninitialize()` / `OleUninitialize()` sequence between `SingleThreadedApartmentTaskScheduler` and `SingleThreadedApartmentTask`.
2. **Add explicit execution mode for synchronous STA execution:**
   ```csharp
   public enum StaExecutionMode
   {
       DedicatedThread = 0,
       ReuseCurrentStaThread = 1,
   }
   ```
   - `DedicatedThread` (default): matches `SingleThreadedApartmentTask.RunAsync` ("each call owns one OLE-initialized background STA thread, performs a bounded final message pump, and uninitializes OLE before returning"). Safe against unexpected reentrancy or mutating a caller UI thread's message queue.
   - `ReuseCurrentStaThread`: when `StaApartment.IsCurrentThreadSta(verifyNativeApartment: false)` (i.e., `Thread.CurrentThread.GetApartmentState() == ApartmentState.STA`), enters `using var scope = StaApartment.EnterScope(initializeOle: true)` inline on the current thread without spawning a thread and **without** running a destructive `preserveQuit: false` teardown pump on the caller's pre-existing message queue; when the current thread is MTA/unknown, falls back to `DedicatedThread`.
3. **Add synchronous `SingleThreadedApartmentTask.Run` overloads:**
   ```csharp
   public static void Run(Action action, CancellationToken cancellationToken = default);
   public static void Run(Action<StaYield> action, CancellationToken cancellationToken = default);
   public static T Run<T>(Func<T> func, CancellationToken cancellationToken = default);
   public static T Run<T>(Func<StaYield, T> func, CancellationToken cancellationToken = default);
   public static void Run(Action action, StaExecutionMode mode, CancellationToken cancellationToken = default);
   public static T Run<T>(Func<T> func, StaExecutionMode mode, CancellationToken cancellationToken = default);
   ```
   - Rethrows worker exceptions via `ExceptionDispatchInfo.Capture(failure).Throw()`, preserving the original exception type and stack trace (never wrapped in `AggregateException` or `InvalidOperationException`).
   - Checks `cancellationToken.ThrowIfCancellationRequested()` before starting work and before/after invoking the delegate, while **always joining** any started dedicated STA thread before returning. It never abandons a running thread inside a synchronous `Run` call, ensuring enclosing `MutexHelper.RunInMutex(...)` scopes cannot release a cross-process mutex while native code is still mutating shared state.
4. **Add `Action` (`void`) ergonomic overloads across existing APIs:**
   - `SingleThreadedApartmentTask.RunAsync(Action, CancellationToken = default)`
   - `SingleThreadedApartmentTask.RunAsync(Action<StaYield>, CancellationToken = default)`
   - `SingleThreadedApartmentTask.RunWithTimeoutAsync(TimeSpan, Action, CancellationToken = default)`
   - `MutexHelper.RunInMutex(string, Action)`
   - `MutexHelper.RunInMutex(string, TimeSpan, Action)`
   - `MutexHelper.RunInMutex(string, TimeSpan, bool, Action)`
   - `MutexHelper.RunInMutex(string, MutexExecutionOptions, Action, CancellationToken = default)`
   - `SingleThreadedApartmentTaskSchedulerExtensions` (extension methods on `ISingleThreadedApartmentTaskScheduler` so existing external implementations of `ISingleThreadedApartmentTaskScheduler` are unbroken):
     - `RunAsync(this ISingleThreadedApartmentTaskScheduler, Action, CancellationToken = default)`
     - `RunAsync(this ISingleThreadedApartmentTaskScheduler, Action, TimeSpan, CancellationToken = default)`

#### Acceptance
- Tests verify synchronous `SingleThreadedApartmentTask.Run` from MTA threads (`DedicatedThread` and `ReuseCurrentStaThread`), inline fast-path from an existing STA thread (`ReuseCurrentStaThread` preserves caller `ManagedThreadId` and leaves `WM_QUIT` untouched), fresh-thread isolation under `DedicatedThread` even when called from an STA thread, exact exception stack preservation via `ExceptionDispatchInfo`, pre-canceled `CancellationToken` fast exit, Nano Server `CO_E_NOTINITIALIZED` recovery on both `Run` and `RunAsync`, and composition inside `MutexHelper.RunInMutex`.

### THR-08 (P1): Managed culture & Win32 thread locale (`SetThreadLocale`) pinning and hygiene

#### Evidence
- Stateful VB6 and Delphi STA COM session wrappers set `CultureInfo.CurrentCulture = CultureInfo.InvariantCulture`, `CultureInfo.CurrentUICulture = CultureInfo.InvariantCulture`, and `kernel32!SetThreadLocale(0x0809)` during session construction and before every calculation call.
- `StaWorkItem<T>` executes delegates directly in the STA worker thread's `ExecutionContext` without capturing caller `ExecutionContext`, which means:
  1. Setting managed culture and Win32 thread LCID on the owned STA thread persists across queued items on both `.NET Framework` and `.NET 10`/`11`.
  2. Conversely, any work item or native COM library that mutates `CultureInfo.CurrentCulture` or calls `SetThreadLocale` mid-call poisons subsequent work items unless restored.

#### Design
1. **Scheduler options (`SingleThreadedApartmentTaskSchedulerOptions`):**
   ```csharp
   public CultureInfo? ThreadCulture { get; set; }
   public CultureInfo? ThreadUICulture { get; set; }
   public int? WindowsThreadLocaleId { get; set; }
   public bool ResetThreadCultureAndLocaleAfterWorkItem { get; set; }
   ```
   - Defaults are `null`, `null`, `null`, and `false` (zero behavioral change unless configured).
   - Validation in constructor: if `WindowsThreadLocaleId is <= 0`, throw `ArgumentOutOfRangeException(nameof(options))`.
2. **Win32 P/Invoke & `StaPlatform` virtual seam:**
   - Add `kernel32!GetThreadLocale()` (`uint`) and `kernel32!SetThreadLocale(uint locale)` (`bool`, `SetLastError = true`) to `NativeMethods` (`[LibraryImport]` on `NET8_0_OR_GREATER`, `[DllImport]` on `.NET Framework`).
   - Add `virtual uint GetThreadLocale()` and `virtual void SetThreadLocale(uint localeId)` on `StaPlatform` (throwing `Win32Exception(Marshal.GetLastWin32Error())` when `SetThreadLocale` returns `false`).
3. **Worker lifecycle order in `SingleThreadedApartmentTaskScheduler`:**
   - Apply configured `ThreadCulture`, `ThreadUICulture`, and `WindowsThreadLocaleId` in `ThreadEntry` **before** `CreateThreadScope` so COM server initialization (`DllMain`, Delphi unit initialization, VB6 runtime startup) observes the pinned culture and Win32 LCID immediately. If `SetThreadLocale` fails for an unsupported LCID, `_threadReady` faults deterministically during scheduler construction.
   - When `ResetThreadCultureAndLocaleAfterWorkItem` is `true`, re-verify after `CreateThreadScope` and in `ExecuteWork<T>.finally` using fast equality checks before writing (`!ReferenceEquals(CultureInfo.CurrentCulture, _threadCulture)` and `_platform.GetThreadLocale() != targetLcid`) so unmutated calls pay no unnecessary locale-switch cost while poisoned state is healed before the next work item.
4. **Standalone `ThreadCultureScope` (`[SupportedOSPlatform("windows")]` on LCID-accepting overload, portable on `CultureInfo`-only overload):**
   ```csharp
   public sealed class ThreadCultureScope : IDisposable
   {
       public static ThreadCultureScope Enter(CultureInfo? culture, CultureInfo? uiCulture = null);
       public static ThreadCultureScope Enter(CultureInfo? culture, CultureInfo? uiCulture, int? windowsThreadLocaleId);
       public void Dispose();
   }
   ```
   - Captures `ThreadAffinity.Capture()`, previous `CultureInfo.CurrentCulture`, previous `CultureInfo.CurrentUICulture`, and (when `windowsThreadLocaleId` is specified on Windows) previous `GetThreadLocale()`, restoring all saved values on `Dispose()` on the owning thread. Enables stateful COM and native session callers running inside `ExecutionWorkerPool` or `SingleThreadedApartmentTask.Run` to pin and restore both managed culture and Win32 LCID cleanly.

#### Acceptance
- Unit tests verify:
  - Constructor validation rejects non-positive `WindowsThreadLocaleId` and surfaces `Win32Exception` if `StaPlatform.SetThreadLocale` fails.
  - `CreateThreadScope` and queued work items observe pinned `InvariantCulture` and Win32 LCID (`0x0809` / `0x0409`) even when the constructing caller thread runs under `pl-PL` or `fr-FR` (comma decimal separator).
  - When `ResetThreadCultureAndLocaleAfterWorkItem = true`, a work item that mutates `CultureInfo.CurrentCulture` to `pl-PL` and calls `SetThreadLocale(0x0415)` is automatically healed before the next work item executes.
  - `ThreadCultureScope` restores prior culture/UI culture/Win32 LCID on `Dispose()`, is idempotent, and throws `InvalidOperationException` on wrong-thread disposal.

### THR-09 (P1): `ValueTask` & cooperative linked-deadline overloads on `TaskExtension.TimeoutAfterAsync`

#### Evidence
- Downstream pooled-dispatcher timeout helpers implement linked-deadline cancellation + single-consumption `ValueTask<TResult>` awaiting + fault observation on wait abandonment + caller-vs-deadline cancellation disambiguation.
- Adding `System.Threading.Tasks.Extensions` to `net472`–`net481` would introduce a new NuGet dependency for `.NET Framework` consumers; guarding `ValueTask` overloads under `#if NET8_0_OR_GREATER` keeps zero added package dependencies while covering `net10.0` and `net11.0` where pooled `ValueTask` (`IValueTaskSource`) dispatchers live.

#### Design
1. **Cooperative linked-deadline delegate overloads (all 5 TFMs: `net11.0`, `net10.0`, `net481`, `net48`, `net472`):**
   ```csharp
   public static Task TimeoutAfterAsync(
       Func<CancellationToken, Task> operation,
       TimeSpan timeout,
       CancellationToken cancellationToken = default);

   public static Task<TResult> TimeoutAfterAsync<TResult>(
       Func<CancellationToken, Task<TResult>> operation,
       TimeSpan timeout,
       CancellationToken cancellationToken = default);
   ```
   - Validates `operation` (`ArgumentNullException`) and `timeout` (`TimeoutValidation.Validate`).
   - Fast path if `cancellationToken.IsCancellationRequested`: returns `Task.FromCanceled(cancellationToken)` without invoking `operation`.
   - Fast path if `timeout == Timeout.InfiniteTimeSpan`: invokes `operation(cancellationToken)` directly without allocating a linked `CancellationTokenSource` or delay timer.
   - Otherwise creates a linked `CancellationTokenSource(cancellationToken)` scheduled with `CancelAfter(timeout)` (disposed only after the underlying task settles so cooperative tokens remain valid during execution, matching `SingleThreadedApartmentTaskScheduler.FinishWaitAsync`), passes `deadline.Token` to `operation`, bounds the caller's wait via `TaskWait`, registers `TaskWait.ObserveFault(pending)` if the wait ends via timeout/cancellation before `pending` completes, and classifies outcomes deterministically:
     - Completed `pending` before wait abandonment preserves exact result/exception (including faulted non-matching `OperationCanceledException`).
     - Caller `cancellationToken.IsCancellationRequested` -> canceled with `cancellationToken`.
     - Deadline expiry without caller cancellation -> faulted with `TimeoutException` even if `operation` cooperatively threw `OperationCanceledException(deadline.Token)`.
2. **`ValueTask` & `ValueTask<TResult>` overloads (`#if NET8_0_OR_GREATER` — `net10.0` and `net11.0`, zero extra dependencies):**
   ```csharp
   #if NET8_0_OR_GREATER
   public static ValueTask TimeoutAfterAsync(
       this ValueTask task,
       TimeSpan timeout,
       CancellationToken cancellationToken = default);

   public static ValueTask<TResult> TimeoutAfterAsync<TResult>(
       this ValueTask<TResult> task,
       TimeSpan timeout,
       CancellationToken cancellationToken = default);

   public static ValueTask TimeoutAfterAsync(
       Func<CancellationToken, ValueTask> operation,
       TimeSpan timeout,
       CancellationToken cancellationToken = default);

   public static ValueTask<TResult> TimeoutAfterAsync<TResult>(
       Func<CancellationToken, ValueTask<TResult>> operation,
       TimeSpan timeout,
       CancellationToken cancellationToken = default);
   #endif
   ```
   - **Single-consumption `IValueTaskSource` invariant:**
     - Validates `timeout` first.
     - If `task.IsCompletedSuccessfully`, consumes the `ValueTask` synchronously once (`task.GetAwaiter().GetResult()`) and returns a completed `ValueTask` / `ValueTask<TResult>` with **zero heap allocation** (no `.AsTask()`, no `TaskCompletionSource`, no timer).
     - Otherwise materializes `var asTask = task.AsTask()` **at most once**, attaches `TaskWait.ObserveFault(asTask)` if abandoned, and delegates to the `Task` timeout monitor wrapped back in `new ValueTask(...)`.

#### Acceptance
- Portable tests (`Trait("Category", "Portable")`, running in `-Mode Portable` as well as Windows/X86) verify:
  - Pooled `ManualResetValueTaskSourceCore<T>` is consumed **strictly once** across synchronous completion, asynchronous completion, timeout abandonment, caller cancellation, and late fault after abandonment (throwing if `GetStatus`/`GetResult` is touched twice).
  - Zero `.AsTask()` allocation on already-completed `ValueTask<int>` fast path.
  - Cooperative `Func<CancellationToken, Task<TResult>>` cancels the inner token on timeout, surfaces `TimeoutException` (not `TaskCanceledException`) when only the deadline token fired, surfaces `OperationCanceledException(callerToken)` when the caller canceled, and suppresses `UnobservedTaskException` when an abandoned operation later faults.

### THR-10 (P2): Configurable `MaxStackSize` on `SingleThreadedApartmentTaskSchedulerOptions` and `SingleThreadedApartmentTask`

#### Evidence
- 32-bit native Fortran/Delphi/PowerBASIC/VB6 engines can overflow constrained IIS/container default stacks, while multi-instance `win-x86` hosts have a 2 GB user-mode virtual address ceiling where explicit stack reservation control matters.

#### Design
1. Add `public int MaxStackSize { get; set; }` (`0` default = runtime/PE default stack size) to `SingleThreadedApartmentTaskSchedulerOptions`:
   - `ValidateConstructorArguments` throws `ArgumentOutOfRangeException(nameof(options), "MaxStackSize must be non-negative.")` when `MaxStackSize < 0`.
   - Construct `_thread` via `_maxStackSize > 0 ? new Thread(ThreadEntry, _maxStackSize) : new Thread(ThreadEntry)`.
2. Add `SingleThreadedApartmentTaskOptions` for configurable one-off STA runs (covering `THR-06`, `THR-08`, and `THR-10` together without combinatorial overload explosion):
   ```csharp
   public sealed class SingleThreadedApartmentTaskOptions
   {
       public string ThreadName { get; set; } = "STA Task Thread";
       public int MaxStackSize { get; set; }
       public StaExecutionMode ExecutionMode { get; set; } = StaExecutionMode.DedicatedThread;
       public Action? BeforeThreadStart { get; set; }
       public bool VerifyNativeStaApartment { get; set; } = true;
       public CultureInfo? ThreadCulture { get; set; }
       public CultureInfo? ThreadUICulture { get; set; }
       public int? WindowsThreadLocaleId { get; set; }
       public bool ResetFloatingPointMaskBeforeExit { get; set; }
   }
   ```
   - Expose `SingleThreadedApartmentTask.Run(..., SingleThreadedApartmentTaskOptions? options, CancellationToken = default)` and `RunAsync(..., SingleThreadedApartmentTaskOptions? options, CancellationToken = default)`.

#### Acceptance
- Unit tests verify negative `MaxStackSize` throws `ArgumentOutOfRangeException`, `MaxStackSize = 0` uses default `Thread` construction, and positive `MaxStackSize` (e.g., `4 * 1024 * 1024`) successfully executes deep recursive stack frames on both x86 and x64 that would overflow a default 256 KB–1 MB stack.
