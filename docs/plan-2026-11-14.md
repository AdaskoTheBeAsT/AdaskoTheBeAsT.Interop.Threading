# STA Threading, Message Pumping & Cross-Library Alignment Plan (2026-11-14)

## Review update (2026-11-15)

Only this dated plan is active; existing `astra_plan.md` work is not reopened.
The scheduler already calls `StaPlatform.Initialize` (`OleInitialize`) and
supports admission limits and diagnostics. Preserve those contracts.

- **THR-01:** `BeforeThreadStart` executes on the constructing thread, before
  `Thread.Start` can trigger CoreCLR's native STA initialization. Capture the
  option values before starting. Verify the native apartment after existing OLE
  initialization, propagate changed-mode failures and balance only successfully
  acquired initialization references. Keep non-Windows/test platform behavior.
- **THR-02:** `CreateThreadScope` is the chosen lifecycle API (not a second pair
  of competing init/exit callbacks). Create once and dispose once on the owned
  thread. Cover startup failure, failed scope creation, queued work, self-dispose,
  repeated/concurrent disposal and scope-disposal exceptions. Preserve existing
  shutdown outcome semantics and ensure every accepted task completes.
- **THR-03:** add bounded pumping without introducing unbounded reentrancy or
  consuming `WM_QUIT`. Scope disposal, native library cleanup, final pump and
  owned OLE uninitialization have explicit order. New message-drain and library
  unload behavior is opt-in (zero/false defaults), not a silent behavior change.
- **THR-04:** floating-point hygiene is opt-in and Windows-x86-specific. Clear
  pending x87/SSE exceptions before restoring safe masks. Do not alter callers'
  rounding/precision modes. Run a real native trap-poisoning fixture in a fresh
  x86 process; simulated platform calls alone do not establish hardware safety.
- **THR-05:** document dependency-free startup wiring to COM preparation and
  thread scopes, and the choice between this single-STA scheduler and typed
  Execution pools. Explain that timeout/cancellation stops the caller's wait,
  not a running synchronous native operation or its session lifetime.

Validation includes startup/teardown event ordering and native apartment tests,
bounded message-pump and `WM_QUIT` tests, x86/x64 Windows runs, and all retained
TFM builds. Do not require a hard dependency on COM or Unmanaged.

### Implementation record

Implemented in `v5.0.0` alongside the `.NET 11` target update (`net11.0`, `net10.0`, `net481`, `net48`, `net472`; `net9.0` and `net8.0` removed; SDK `11.0.100`):

- **THR-01 (`BeforeThreadStart` & `VerifyNativeStaApartment`):** Options are snapshotted at construction before `BeforeThreadStart` executes synchronously on the caller thread prior to `Thread.Start()`. On the worker thread, after `StaPlatform.Initialize()` (`OleInitialize`), `EnsureNativeStaApartment` queries `combase!CoGetApartmentType`, recovers `CO_E_NOTINITIALIZED` via `CoInitializeEx(COINIT_APARTMENTTHREADED)`, propagates `RPC_E_CHANGED_MODE` and negative HRESULTs, accepts `APTTYPE_STA`, `APTTYPE_MAINSTA`, and STA-hosted `APTTYPE_NA` (`APTTYPEQUALIFIER_NA_ON_STA` / `APTTYPEQUALIFIER_NA_ON_MAINSTA`), faults construction with `InvalidOperationException` on MTA/other apartments, and balances `CoUninitialize` / `OleUninitialize` strictly for acquired references.
- **THR-02 (`CreateThreadScope`):** Implemented `Func<IDisposable?>? CreateThreadScope` as the single thread-scope lifecycle hook (created once on the owned STA thread before `_threadReady`, disposed once on the owned STA thread during shutdown after `DrainQueue(failure)` so scope-disposal exceptions fault `Completion`/`ShutdownAsync` while preserving canceled status on pending items).
- **THR-03 (`PostWorkItemMessagePumpBatchSize` & `FreeUnusedComLibrariesOnShutdown`):** Opt-in defaults (`0` and `false`), rejecting negative batch sizes with `ArgumentOutOfRangeException`. Bounded post-work-item and final shutdown pumps preserve `WM_QUIT` (`preserveQuit: true`). Explicit teardown order on the owned STA thread: `Scope.Dispose()` -> `CoFreeUnusedLibrariesEx(0, 0)` -> bounded final pump (`preserveQuit: true`) -> owned `CoUninitialize()` -> owned `OleUninitialize()`.
- **THR-04 (`ResetFloatingPointMaskAfterWorkItem`):** Opt-in (`false` default), active only on Windows `Architecture.X86`. Real x86 hardware validation uncovered three critical runtime requirements: (1) `_controlfp_s` strips `_EM_DENORMAL` (`0x00080000`) on x86, so `ucrtbase!__control87_2(McwEm, McwEm, out _, out _)` is used after `ucrtbase!_clearfp()` to mask all six exceptions in both x87 FCW and SSE2 `MXCSR` without modifying rounding (`_MCW_RC`) or precision (`_MCW_PC`); (2) `ResetFloatingPointState()` is invoked once on worker startup *before* `CreateThreadScope` so virtual dispatch, managed wrapper, and P/Invoke stubs are JIT-compiled and bound before any native callback can arm pending traps (preventing `clrjit.dll` stack/FPU faults on first call in fresh processes); and (3) per-work-item reset runs first inside `ExecuteWork`'s `finally` block before diagnostics `Stopwatch.Elapsed.TotalMilliseconds` (`double` division) or task completion.
- **THR-05 (Documentation):** Updated `docs/using-with-adaskothebeast-interop-com.md`, `README.md`, `CHANGELOG.md`, `MIGRATION.md`, `docs/validation.md`, and `benchmarks/README.md`.

## Executive summary

`SingleThreadedApartmentTaskScheduler` (`v4.0.1`) already incorporates strong lifecycle ownership, cooperative cancellation (`RunCooperativeAsync`), `WM_QUIT` preservation, and `StaYield` helpers. Production testing of legacy 32-bit STA COM workloads on Windows Nano Server 2025 and high-concurrency multi-STA-worker hosts surfaced **five concrete improvements**:

1. **Nano Server STA initialization ordering (`NanoServerOptions` / `nanoserver_sta_shim` readiness before `Thread.SetApartmentState(ApartmentState.STA)`):**
   - On Windows Nano Server without `win32u.dll`, CoreCLR calls `combase!CoInitializeEx(COINIT_APARTMENTTHREADED)` **at OS thread startup** inside `Thread.Start()` before the managed `ThreadEntry` delegate ever runs!
   - If the OS-level `nanoserver_sta_shim.dll` is not present (or if a process relies on `AdaskoTheBeAsT.Interop.COM`'s in-process STA shim before `NanoServerOptions` has been touched), starting a `SingleThreadedApartmentTaskScheduler` before STA shim hooks are active causes CoreCLR's initial `CoInitializeEx(STA)` to fall back to MTA or fail, or leaves `ThreadEntry` without an explicit `CoInitializeEx(COINIT_APARTMENTTHREADED)` verification check.
2. **`CoFreeUnusedLibrariesEx` & post-work-item STA message drain hook during teardown and idle transitions:**
   - Legacy VB6 (`MSVBVM60.DLL`), Delphi VCL (`Classes.MakeObjectInstance` hidden HWND), and Jet 4.0 / ADO STA servers post deferred COM marshaling/cleanup messages to the STA thread's message queue when RCWs are released and retain in-proc DLL locks until `CoFreeUnusedLibrariesEx` + a bounded `PeekMessageW` drain run **on that exact STA thread** prior to `CoUninitialize`.
3. **x87 FPU control-word preservation across STA work items (`win-x86`):**
   - 32-bit Delphi and Fortran/C++ COM servers executed inside `SingleThreadedApartmentTaskScheduler` unmask x87 floating-point hardware traps (`#ZE`, `#OE`, `#IE`) on the owned STA thread, causing subsequent work items or task continuations on the STA thread to crash with `STATUS_FLOAT_DIVIDE_BY_ZERO` (`0xC000008E`) unless the STA loop masks x87 exceptions after user delegates.
4. **Thread-init & thread-exit lifecycle hooks (`Action` callbacks on the owned STA thread):**
   - Callers combining `SingleThreadedApartmentTaskScheduler` with `AdaskoTheBeAsT.Interop.COM` currently re-activate and deactivate SxS manifests on *every* `RunAsync` call (`docs/using-with-adaskothebeast-interop-com.md:88-100`), paying repeated `CreateActCtxW` / `CoRegisterClassObject` overhead instead of activating a per-STA-thread scope once at thread start and disposing it on the STA thread before `ThreadEntry` exits!
5. **Clear architectural guidance in `docs/` comparing `SingleThreadedApartmentTaskScheduler` vs `AdaskoTheBeAsT.Interop.Execution` (`ExecutionWorkerPool<TSession>` with `ApartmentState.STA`):**
   - Consumers need explicit guidance on when to choose `AdaskoTheBeAsT.Interop.Threading` (cooperative `StaYield` message pumping, per-call timeouts, named cross-process mutexes, ad-hoc heterogeneous delegates on one STA thread) versus `AdaskoTheBeAsT.Interop.Execution` (multi-worker STA pool with typed stateful `TSession`, `LeastQueued` routing, session recycling, and ASP.NET Core `IHostedService` lifecycle).

## Detailed technical plan

### THR-01 (P0): Verify native COM STA initialization inside `ThreadEntry` & pre-start hook

#### Evidence
- `StaPlatform.Start(Thread)` sets `thread.SetApartmentState(ApartmentState.STA)` and starts the thread.
- On Windows Nano Server 2025 when neither the OS-level `nanoserver_sta_shim.dll` nor `NanoServerOptions.EnsureInitialized()` has run before `new SingleThreadedApartmentTaskScheduler()`, CoreCLR's implicit startup `CoInitializeEx(COINIT_APARTMENTTHREADED)` fails silently (`E_NOTIMPL` / `CO_E_NOTSUPPORTED`), leaving the thread uninitialized or in MTA (`APTTYPE_MTA`) while `Thread.GetApartmentState()` still reports `ApartmentState.STA`!

#### Design
1. Add `public Action? BeforeThreadStart { get; set; }` to `SingleThreadedApartmentTaskSchedulerOptions` so callers on Nano Server can wire `BeforeThreadStart = NanoServerOptions.RefreshStaState` (without adding a hard package dependency from `Interop.Threading` to `Interop.COM`).
2. Inside `StaPlatform` on `ThreadEntry` startup, call `CoGetApartmentType(out var aptType, out var aptQualifier)`:
   - If `CO_E_NOTINITIALIZED`, explicitly call `CoInitializeEx(IntPtr.Zero, COINIT_APARTMENTTHREADED)` and track ownership so `ThreadEntry` balances `CoUninitialize()` on exit.
   - If `VerifyNativeStaApartment` (default `true` on Windows) detects `APTTYPE_MTA` / `APTTYPE_IMPLICIT_MTA`, fault `_threadReady` immediately with a clear `InvalidOperationException` explaining that native `COINIT_APARTMENTTHREADED` failed (pointing Nano Server users to `nanoserver_sta_shim` / `NanoServerOptions`).

#### Acceptance
- Simulated `StaPlatform` unit tests verify explicit `CoInitializeEx(STA)` recovery on `CO_E_NOTINITIALIZED`, balanced `CoUninitialize` on shutdown, and deterministic constructor failure if the thread lands in native MTA.

### THR-02 (P0): Owned STA thread lifecycle callbacks (`OnThreadInitialized` / `OnThreadShuttingDown`)

#### Evidence
- In `docs/using-with-adaskothebeast-interop-com.md` (`lines 82-104`), `ScheduledComCalculator` calls `Executor.Execute(_comDllPath, _manifestPath, ...)` inside every `RunAsync` lambda.
- For COM calculation libraries whose SxS manifest registers 10–30 coclasses or loads large native dependencies, activating and deactivating the manifest on every calculation adds measurable per-call overhead and prevents keeping stateful COM objects (`IDatabase`, `ISelector`) alive across calls on the scheduler's STA thread.

#### Design
Add optional thread-affinitized callbacks to `SingleThreadedApartmentTaskSchedulerOptions`:
```csharp
public Func<IDisposable?>? CreateThreadScope { get; set; }
```
- Invoked once inside `ThreadEntry` on the STA thread immediately before signaling `_threadReady`.
- If `CreateThreadScope` throws, `_threadReady` faults with that exception and the worker exits cleanly without leaking wait handles.
- When the scheduler shuts down (after the work queue drains/cancels and before OLE uninitialization), the returned `IDisposable` is disposed **on the exact same STA thread**, guaranteeing thread-affinitized `DeactivateActCtx` / `CoRevokeClassObject` / `Marshal.FinalReleaseComObject` semantics!

#### Acceptance
- Tests verify `CreateThreadScope` runs on `_thread.ManagedThreadId`, its `Dispose()` runs on `_thread.ManagedThreadId` during `scheduler.Dispose()`, and exceptions in `CreateThreadScope` fail construction cleanly without leaked background threads.

### THR-03 (P1): Post-work-item message drain & `CoFreeUnusedLibrariesEx` during STA teardown

#### Evidence
- Releasing RCWs or VB6/Delphi STA objects queues hidden window cleanup messages (`WM_DESTROY` / `OLE` channel rundown) to the STA thread's Win32 message queue.
- When `SingleThreadedApartmentTaskScheduler.Dispose()` exits `ThreadEntry` without a final bounded message pump + `CoFreeUnusedLibrariesEx(0, 0)`, in-process COM DLLs with `DllCanUnloadNow` remain mapped or skip window teardown before thread termination.

#### Design
1. Add `public int PostWorkItemMessagePumpBatchSize { get; set; } = 64;` (opt-in `> 0` or default `64`) and `public bool FreeUnusedComLibrariesOnShutdown { get; set; } = true;` on `SingleThreadedApartmentTaskSchedulerOptions`.
2. After each completed work item, pump up to `PostWorkItemMessagePumpBatchSize` pending messages (`PeekMessageW(..., PM_REMOVE)` preserving `WM_QUIT`).
3. During `ThreadEntry` shutdown (after `CreateThreadScope` disposal and before `CoUninitialize`), call `ole32!CoFreeUnusedLibrariesEx(0, 0)` followed by one bounded message-pump pass.

#### Acceptance
- Native/simulated `StaPlatform` tests verify `WM_QUIT` preservation, bounded non-blocking message drain after work items, and `CoFreeUnusedLibrariesEx` invocation order (`Scope.Dispose` -> `CoFreeUnusedLibrariesEx` -> final pump -> `CoUninitialize`).

---

### THR-04 (P1): Opt-in x86 floating-point mask hygiene (`ResetFloatingPointMaskAfterWorkItem`)

#### Evidence
- On 32-bit `win-x86`, Borland Delphi and legacy C++/Fortran COM methods unmask x87 FPU exceptions on the STA thread, poisoning subsequent managed floating-point operations scheduled onto the same `SingleThreadedApartmentTaskScheduler`.

#### Design
- Add `public bool ResetFloatingPointMaskAfterWorkItem { get; set; } = true;` (active only on Windows `Architecture.X86`) calling `msvcrt!_controlfp_s(out _, _MCW_EM, _MCW_EM)` + `_clearfp()` after `CreateThreadScope` and after each work item in `ThreadEntry`.

#### Acceptance
- On `x86` test runs, a work item that unmasks x87 `#ZE` / `#IE` does not cause the next work item computing `0.0 / 0.0` (`double.NaN`) to fault the STA thread.

---

### THR-05 (P2): Documentation alignment across `Threading`, `COM`, and `Execution`

Update `docs/using-with-adaskothebeast-interop-com.md` with:
1. Using `CreateThreadScope` + `AdaskoTheBeAsT.Interop.COM`'s activation scope to keep SxS/Nano Server class factories active for the lifetime of the STA thread rather than re-activating per call.
2. Configuring `BeforeThreadStart = NanoServerOptions.RefreshStaState` when targeting Windows Nano Server without the OS-level STA shim.
3. A decision matrix comparing:
   - **`AdaskoTheBeAsT.Interop.Threading` (`SingleThreadedApartmentTaskScheduler`):** Best for single-STA orchestration, cooperative `StaYield` pumping inside long COM batches, per-call timeouts, and named cross-process `Mutex` coordination.
   - **`AdaskoTheBeAsT.Interop.Execution` (`ExecutionWorkerPool<TSession>` with `ApartmentState.STA`):** Best for multi-worker horizontal scaling of isolated native/COM sessions (`WorkerCount = N`), `LeastQueued` routing, `MaxOperationsPerSession` recycling, OpenTelemetry metrics, and ASP.NET Core `IHostedService` hosting.
